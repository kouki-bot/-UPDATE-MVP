# 山口ローカルUPDATE

山口県内の店舗・商業サービスに関する新店・開店、閉店、移転、リニューアル情報を収集し、人による確認を経て公開するサイトです。

- 公開サイト: https://local-life-lab.github.io/-UPDATE-MVP/
- 管理画面: https://local-life-lab.github.io/-UPDATE-MVP/admin/review.html
- 公開リポジトリ: https://github.com/local-life-lab/-UPDATE-MVP
- 非公開の承認管理リポジトリ: local-life-lab/yamaguchi-review-private

## 運営上の基本ルール

1. 自動収集は候補作成まで。収集した候補をそのまま公開しない。
2. 店舗名・所在地・日付・営業状況・情報源を人が確認する。
3. 閉店・移転・リニューアルなど既存店舗の状態変化は特に慎重に確認する。
4. 写真は利用許可または利用条件・出典・クレジットを確認できたものだけ掲載する。確認できない場合はデザイン済みプレースホルダーを使う。
5. 宿泊施設、観光・レジャー、公共・地域施設、イベント・催事、期間限定ポップアップは対象外。
6. 確認できない情報は無理に掲載せず、保留または除外する。

## 自動ワークフロー

### 情報収集: Yamaguchi Local Update

ファイル: `.github/workflows/update.yml`

- 定期実行: 毎日 00:00 UTC（日本時間 09:00）
- 手動実行: GitHub Actions から可能
- 公式サイト・RSS候補を収集し、審査用下書きを生成
- 安全性テスト、候補レポート、出典リンク確認、掲載済み店舗の状態変化チェックを実行
- 候補データを成果物として保存し、非公開の承認管理リポジトリへ同期
- 候補は「未確認・公開禁止」のまま保持

このワークフローは公開記事を更新しません。手動実行しても公開処理は行われません。

### 承認済み記事の公開: Publish Manually Approved Articles

ファイル: `.github/workflows/publish-approved.yml`

- 定期実行: UTC 毎時 07分・37分（日本時間でも毎時 07分・37分）
- `main` ブランチを対象に実行
- 非公開リポジトリから承認記録を取得し、公開条件を満たす記事だけを公開データへ反映
- SEO記事ページと `sitemap.xml` を再生成
- 変更がある場合だけ `main` にコミット
- 承認データの空化・大量欠落による一括取り下げは安全装置で停止
- 意図的な一括取り下げだけ、手動実行時に専用入力を明示的に有効化

GitHub Actions の定期実行は混雑等で遅れる場合があります。設定時刻ちょうどの実行を保証するものではありません。

## 公開条件（主なゲート）

新規記事は、少なくとも次の条件をすべて満たす必要があります。

- 対象区分が `店舗・商業施設`
- `manual_hold` が `true` ではない
- 管理画面で人による確認・承認が完了している
- 店舗名、所在地、記事公開日、店舗動作日、営業状況、情報源の6項目を確認済み
- 情報源を実際に確認した記録と確認日時がある
- 最終確認から7日以内
- 主出典と追加出典のURL確認がすべて `ok`
- 必須項目、日付、営業状況、重複確認などの追加条件を満たす
- 未解消の確認フラグがない

既存記事と新規記事では一部の判定条件が異なります。管理画面の公開準備表示は判定理由を示すもので、承認や公開を代行するものではありません。

## 一括取り下げの安全装置

- 公開済み記事がある状態で承認IDが0件なら、公開処理を停止します。
- 既存記事の25%（最低4件相当）を超える大量取り下げも自動では実行しません。
- 意図的に一括取り下げる場合は、GitHub Actions の `Publish Manually Approved Articles` を手動実行し、`allow_bulk_withdrawal` を有効にします。通常運用では無効のままにしてください。
- 承認IDに対応する審査記録がない、または候補・公開済みデータのどちらにも存在しないIDがある場合も停止します。

## 日常の確認手順

### 毎日の収集後

1. GitHub Actions で `Yamaguchi Local Update` の最新実行を開く。
2. すべてのステップが成功しているか確認する。
3. 安全性テストと「未確認・公開禁止」の検証が通っているか確認する。
4. 成果物・非公開承認管理リポジトリへの同期結果を確認する。
5. 管理画面で候補を確認し、根拠が不足するものは保留する。

### 公開前

1. 店舗の公式サイト・公式SNS等で最新情報を確認する。
2. 店舗名、所在地、開店・閉店等の日付、現在の営業状況を照合する。
3. 出典URLが正しいページを指し、アクセス可能か確認する。
4. 写真を使う場合は利用権限・クレジットを確認する。
5. 6項目の確認と承認記録を完了する。
6. 管理画面の公開準備表示でブロック理由が残っていないことを確認する。

承認条件を満たさない候補は公開しません。候補数を増やす目的で確認基準を緩めないでください。

## 主なデータ

- `data/source_checks.json`: 公式情報源から収集した候補
- `data/rss_candidates.json`: RSS等から収集した候補
- `data/drafts.json`: 審査用下書き
- `data/excluded_candidates.json`: 対象外として除外した候補の監査記録
- `data/published.json`: 公開対象の記事データ
- `data/publication_approvals.json`: 承認記録（公開リポジトリへ置かない）

承認記録やトークン等の秘密情報を公開リポジトリへコミットしないでください。

## トラブル時

- 収集ワークフローが失敗: Actions の失敗ステップとログを確認し、原因を修正してから再実行する。
- 候補が少ない: 収集元の更新頻度、取得制限、RSS本文・日付の取得状況を確認する。候補数を増やす目的で未確認情報を公開しない。
- 出典URLが確認不能: アクセス制限や一時障害の可能性も含め、人が確認する。
- 公開されない: 管理画面の公開準備表示とワークフローのログを確認する。条件を満たさない候補を無理に公開しない。
- 非公開リポジトリへの同期失敗: 認証設定と同期ログを確認する。秘密情報をチャットや公開Issueに貼らない。

## 変更時のルール

- 機能変更はブランチとPull Requestで行い、差分・テスト・公開への影響を確認する。
- `main` へ直接変更しない。
- 公開処理、承認条件、対象範囲を変更する場合は、通常の表示改善とは分けてレビューする。
- Pull Request は安全性テストを確認してから手動でマージする。
